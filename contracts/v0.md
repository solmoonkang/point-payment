# 킵페이 ↔ 제로페이 연동 규격 v0

> 코드 기준: `packages/contract/src/` (zod) · 예시: `contracts/fixtures/v0.json`
> 로컬 시나리오용 초안이다. 실제 제로페이 · 쿠콘 규격이 나오면 이 문서와 계약 패키지를 함께 고친다.

## 1. 역할 나눔

| 단계 | 제로페이 | 킵페이 |
|---|---|---|
| 이동 | 킵페이 주소로 링크만 둠 | - |
| 가입 | 회원 확인 응답 | 고객정보 입력 뒤 회원 확인 요청, 킵페이 회원 저장 (제로페이 회원 번호 포함, 없으면 카드만) |
| 결제 | 잔액 응답, 사용 요청을 받으면 바로 차감 · 승인 번호 발급 | 사용 요청, 부족 금액 PG 결제, 주문 저장 |
| 취소 | 사용 취소 처리 (사유 기록) | 가입 취소 · 카드 실패 시 PG 취소, 사용 취소 요청 |
| 대조 | 사용 내역 제공 | 승인 번호로 대조 |

## 2. 공통 규칙

| 항목 | 규칙 |
|---|---|
| 가맹점 확인 | 모든 호출에 `x-merchant-key` 헤더 |
| 금액 | 원 단위 정수, 0 이상 |
| 잔액 계산 | 제로페이만 함. 킵페이는 쓸 금액만 보내고 남은 잔액을 보내지 않음 |
| 같은 요청 다시 보내기 | 사용 요청은 `merchantOrderId`(킵페이 주문 번호)가 같으면 처음 승인 번호를 그대로 돌려줌. 내용이 다르면 `conflict` (`ORDER_REUSED`) |
| 사용 취소 | 같은 사용 건에 두 번 와도 한 번만 복원 |
| 실패 응답 | `{ code, error, message }` — code 는 큰 분류(`unauthorized` · `not-found` · `invalid` · `conflict` · `expired` · `unavailable`), error 는 보낸 쪽의 세부 이름(예: `REQUEST_ID_REUSED`). 다시 보내도 되는 것은 `unavailable` 뿐 |

## 3. 호출

| 호출 | 경로 | 보내는 값 | 받는 값 |
|---|---|---|---|
| 회원 확인 | `POST /api/v0/members/verify` | `name`, `birth`, `phone` | `memberId` (없으면 `not-found`) |
| 잔액 조회 | `GET /api/v0/members/:memberId/balance` | - | `balance` (만료되면 0) |
| 사용 요청 | `POST /api/v0/usages` | `memberId`, `amount`, `merchantOrderId` | `approvalNo` · 받는 즉시 차감. 잔액 부족 `INSUFFICIENT_BALANCE`, 만료 `VOUCHER_EXPIRED` 실패 응답 |
| 사용 취소 | `POST /api/v0/usages/:approvalNo/cancel` | `reason` | 사용 건 (`status: cancelled`) |
| 사용 내역 | `GET /api/v0/usages?from=&to=` | 기간 | 사용 건 목록 |

사용 건의 상태는 `approved`(차감 완료) · `cancelled`(사용 취소)다. 거절된 요청은 사용 건을 만들지 않는다.

## 4. 결제 한 건의 순서

```
회원  제로페이에서 「킵페이에서 가입하기」 → 킵페이 보험 선택 (요청 없음)
킵페이  고객정보 입력 뒤 회원 확인 → 가입 → 잔액 조회 → 사용 요청
제로페이  바로 차감 · 승인 번호 응답
킵페이  부족 금액 PG 결제 → 가입 완료
        (PG 실패 시 사용 취소로 상품권 복원)
```

## 5. 실제 연동에서 확인할 것

- 회원 확인을 무엇으로 하는지 (이 저장소는 이름 · 생년월일 · 휴대폰번호, 실제는 본인인증 연계정보 CI 가능성)
- 회원이 제로페이 쪽에서 결제를 한 번 더 승인하는지 (이 저장소는 승인 없이 바로 차감)
- 승인 번호 형식과 정산 파일 형식
